# 10월 과정: 예선까지 혼자 도는 능력

목표는 10/31 예선 형식에 맞춰 **모르는 인물을 인터뷰하고 → 요구를 계약으로 닫고 → 기존 대화형 AI CLI 한 세션에 구현을 시키고 → 미리 고정한 시험으로 검증하고 → 실패 원인을 좁혀 고치는** 전 과정을 혼자 반복하는 것이다. 코딩 문법은 배우지 않는다. 코드는 AI가 쓰고, 네가 묻고·실행하고·판별한다.

## 인물 인터뷰 하는 법

인터뷰는 "뭘 만들어 드릴까"를 묻는 자리가 아니다. 그 사람의 최근 실제 작업 하나를 끝까지 따라가는 자리다.

1. **사건부터**: "최근에 이 일을 실제로 한 순서가 어떻게 돼?" — 일반론이 나오면 "가장 최근 한 건만"으로 좁힌다.
2. **성공의 눈**: "성공인지 무엇을 보면 알아?" — 그 답이 나중에 시험의 기대값이 된다.
3. **비용과 예외**: "잘못됐을 때 가장 큰 비용은?", "자동으로 하면 안 되는 행동은?" — 금지 행동과 승인 경계가 여기서 나온다.
4. **모르는 것 남기기**: 답을 못 들은 항목은 지우지 말고 `미확인`으로 적는다. 인물이 안 말한 것을 말한 것처럼 쓰면 그때부터 구현이 아니라 소설이다.
5. **되읽어 확인**: "내가 이해한 목표는 ___, 가장 중요한 예외는 ___, 자동으로 하지 않을 행동은 ___다. 맞나?" — 틀린 채로 닫지 않는다.

기록은 [인터뷰 양식](../templates/interview.md)을 쓰고, 산출물은 **성공조건 3개·모르는 것·피할 행동·시간 제한** 네 묶음이다. 이 네 개가 [요구 계약](../templates/requirements.md)의 뼈대가 된다.

**가상 인물과 연습할 때**: [인터뷰 실습](../labs/01-interview.md)의 persona 파일은 인터뷰 전에 네가 먼저 읽지 않는다. 답을 알고 묻는 인터뷰는 시험이 아니라 독해다. 파일을 대화형 CLI에 읽히고, 네 질문에 대해 인물 역할로 답하게 한다.

**분류 규칙** — 인터뷰와 자료에서 나온 모든 문장을 셋 중 하나로 표시한다: `사실`(인물이 말했거나 자료에 있는 것), `가정`(네가 채운 해석), `미확인`(아직 묻거나 확인하지 못한 것). 가정과 미확인은 요구 계약의 "가정과 미확인" 표로 옮긴다.

## 작게 도는 에이전트의 정의

10월에 만드는 에이전트는 이 경로 하나다:

```
입력 → 자료 읽기 또는 도구 호출 → 판단 → 출력 형식 검증 → 응답 → 상태 기록
```

- **작다**의 뜻: 성공조건 3개 중 하나를 만족하는 최소 경로. 기능 목록이 아니다.
- **돌았다**의 뜻: 정한 입력을 넣었을 때 기대 형식의 출력 파일이 나온 것. "코드가 생겼다"는 돌았다가 아니다.
- **모의와 실제 구분**: 규칙으로 답을 고르는 오프라인 도구가 돌아도 그것은 모의다. 실제 모델을 쓴 경로, 카카오 네이티브 경로와 섞어 보고하지 않는다(뒤의 증거 분리 참조).

### 계약 예제: 요청·도구·검증·응답·상태

대화형 요청이 들어온다고 가정한 최소 계약(형식은 [카카오 스킬 문서](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/make_skill)(K06)류를 본뜬 학습용이다).

요청(서버가 받는 것):

```json
{
  "requestId": "req-042",
  "userRequest": { "user": { "id": "u-1" }, "utterance": "어제 회의 메모 어디 있지?" }
}
```

응답(서버가 돌려주는 것, 형식 예):

```json
{
  "version": "2.0",
  "template": { "outputs": [ { "simpleText": { "text": "notes/ 폴더의 10-01 회의 메모를 찾았어. 근거: f-12" } } ] }
}
```

- **도구 계약**: 도구마다 이름·입력·출력·실패 시 오류 형식을 정한다. "프로토콜이 깨졌다"(요청 형식 자체가 잘못됨)와 "도구가 실패했다"(형식은 맞지만 실행 실패)를 구분해 응답한다 — [MCP 도구 명세](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)(A07)가 구분하는 두 오류다.
- **검증은 두 층**: 출력이 정해진 형식에 맞는가(형식 검증) + 내용이 자료 근거에 맞는가(의미 검증). 형식 통과가 정답을 뜻하지 않는다 — [JSON Schema 문서](https://json-schema.org/understanding-json-schema/reference/object)(A08)가 다루는 건 형식뿐이다.
- **상태 기록**: 요청 ID, 처리 단계, 마지막 오류를 `state.json` 같은 파일에 남긴다. 세션이 끊겨도 "어디까지 했나"를 다시 읽을 수 있게 — 이미 네가 쓰는 체크포인트 구조다.
- **오류 응답 계약**: 자료 없음 / 자료 충돌 / 도구 실패 세 경우의 응답 문구를 미리 정한다. 모르면 모른다고 답하는 응답도 설계다.

## 평가표 고정과 실패 고치는 순서

평가 규칙은 실행 전에 닫는다. 양식은 [시험표](../templates/eval-sheet.md).

- **N 고정**: 필수 시험 수를 실행 전에 정한다. `N = P + F + U`(통과 + 실패 + 미실행·판정 불가). 미실행 U도 분모에 들어가며, 빼서 분모를 줄이지 않는다. N=0이면 판정 불가다.
- **P/N 기록**: 통과 P를 사전 고정 N으로 나눈다. 미실행은 통과가 아니고 분모에서도 빼지 않는다.
- **B=0**: 핵심 경계 위반(근거 없는 사실 확정, 금지 행동·송신, 비밀 노출 등 시작 전 정한 것)이 하나라도 있으면 불합격.
- **개발용과 확인용 분리**: 고치면서 본 시험과 마지막 판정에 쓸 손대지 않은 시험을 나눈다. 확인용 답을 열어 구현을 고쳤으면 그 문제는 개발용으로 내리고 새 확인용을 확보한다.
- **합격**: P=N, B=0, 미확인 항목의 정확한 명시. 대회 점수를 예측하는 가중치는 만들지 않는다 — 근거가 없다.
- **관찰과 제작물을 나눈다**: 실험·재현·비교 과제는 관찰(N_obs를 사전 고정, 완료는 실행 뒤 C_obs=N_obs일 때)로, 만든 결과물의 합격은 제작물 시험(N_prod=P_prod+F_prod+U_prod>0)으로 별도 기록한다. 관찰 과제의 완료를 제작물 합격으로 세지 않는다.
- **기대값 변경 금지**: 기대값을 바꾸면 새 시험표 버전으로 다시 평가한다. 작성자가 자기 답에 맞춰 채점표를 고치는 것이 평가 실패의 가장 흔한 형태다.

실패했을 때 순서:

1. **재현**: 같은 입력을 다시 넣어 같은 실패를 본다. 재현 안 되면 "언제 되고 언제 안 되나"가 첫 질문.
2. **층 좁히기**: 실패가 입력·자료·도구·모델·상태·환경 중 어디서 나왔는지 후보를 적는다. "AI가 잘못했다"는 층이 아니다.
3. **가설 하나**: 후보 하나만 고르고, 그 후보와 다른 후보를 가를 최소 시험 하나를 정한다.
4. **최소 수정**: 그 원인만 고친다. 다른 기능, 다른 파일, 시험의 N을 같이 건드리지 않는다.
5. **같은 시험 재실행**: 전과 후 출력을 나란히 남긴다. "고쳤다"는 말이 아니라 전후 비교가 증거다.

## 카카오: 다섯 경로와 증거 분리

카카오 관련 기능은 서로 대체가 안 되는 다섯 경로다. 하나의 성공을 다른 경로의 증거로 쓰지 않는다. 근거는 [조사 판정](../research/FINDINGS.md)과 각 문서다.

| 경로 | 되는 일 | 실제 연결 조건 | 오프라인 대안 |
|---|---|---|---|
| [카카오 로그인](https://developers.kakao.com/docs/ko/kakaologin/common)(K01) | 사용자 인증과 동의 범위의 접근 토큰 | 개발자 앱, 로그인 설정, 리다이렉트 | 가상 인증 상태표. 로그인 성공은 대화 수신 성공이 아니다 |
| [나에게 메시지](https://developers.kakao.com/docs/ko/kakaotalk-message/rest-api)(K03) | 본인의 나와의 채팅으로 발송 | 앱·로그인·액세스 토큰·`talk_message` 동의·템플릿 | 본인 대상 가상 발송함. 타인 수신·수신 기능 미입증 |
| [친구 메시지](https://developers.kakao.com/docs/ko/tutorial/message)(K04) | 같은 서비스 친구를 골라 발송 | 양측 친구 관계·앱 연결·동의. 심사 전 일 30건·한 번에 5명, 추가 기능 신청·심사 소요기간 미확인 | 관계·동의 조합 시험표. 임의 사용자 자동 안내 경로가 아니다 |
| [채널 챗봇](https://kakaobusiness.gitbook.io/main/tool/chatbot/tutorial/make_chatbot/tutorial_1)(K05) | 채널 발화를 블록/스킬로 처리·응답 | 봇 마스터 = 채널 매니저 이상, 연결 앱 있으면 EDITOR 이상. 기존 봇·메뉴와 충돌 가능 | 가상 발화 JSON → 응답 JSON 대조 |
| 비공식 개인계정 자동화 | 개인 메신저 화면·통신 조작 | 공식 문서에서 지원 경로로 확인 안 됨 | 채택하지 않는다. 허용·안정성·대회 인정 모두 미확인 |

연동 요건과 시간 제약(조사 확인분):

- **스킬 서버 접근**: 외부 처리를 쓰면 공인 IP 또는 공중망 도메인이 필요하다. localhost에서 잘 돈 것은 카카오가 접근할 수 있다는 증거가 아니다. [K06](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/make_skill)
- **응답 기한**: 일반 스킬 응답 안내는 5초. 콜백 방식은 최초 응답에 `useCallback: true` 후 일회성 URL로 후속 응답. 단, 콜백 유효시간은 같은 문서 안에서 개요 5분 vs 오류 표 1분으로 **상충 — 미확인**으로 둔다. [K07](https://kakaobusiness.gitbook.io/main/tool/chatbot/skill_guide/ai_chatbot_callback_guide)
- **시간 예산 분해**: `응답시간 = 통신 + 대기 + 모델 처리 + 응답 조립`. 모의에서는 교육 설정 예산(예: 4초)을 정해 넘는 사례를 따로 표시한다. 4초는 학습 설정, 5초는 문서 값 — 섞지 않는다.
- **봇테스트 ≠ 실수신**: 봇테스트 통과는 실제 채널 수신의 증거가 아니다. 승인 필수 여부·처리기간도 현재 문서로 미확인.

**연결 진행 게이트**: 실제 연결은 `G = R ∧ A ∧ Q ∧ E`가 모두 `확인`일 때만 한다 — R(공식 요구 방식 확인), A(그 행위에 대한 사용자 승인), Q(계정·권한·비용·제공량 확인), E(시험 환경과 증거 수집 방법). 하나라도 미확인·부정이면 **오프라인 모의 단계로 종료**한다. 현재 R은 미확인이고 송신·설정 행위는 미승인이므로 이 제작 과업에서는 실제 연결을 진행하지 않는다.

**증거는 다섯 칸으로**: `D`=문서 확인, `O`=오프라인 모의 통과, `M`=실제 모델 사용, `K`=카카오 네이티브 왕복, `J`=대회 요건 수용. `O=통과`에서 `M/K/J=통과`를 추론하지 않는다. 기록은 [연결 계약](../templates/channel-contract.md)의 네 층 표에 남긴다.

**실제 연결 전의 별도 체크 두 개**: (1) 모의 입출력 합격 — 로컬 fixture → 어댑터 → 응답 형식 대조가 P=N. (2) 제출 요건 충족 — 공개된 제출 형식과 결과물의 대조. 이 둘은 다른 시험이고 둘 다 남겨야 한다.

## 모의전 3회 (학습 설정)

| 회차 | 날짜 | 교육 설정 시간 | 규칙 |
|---|---|---|---|
| 1 | 10/12 | 90분 | 인터뷰 → 요구 계약 → 최소 구현 → 고정 시험 → 모의 묶음 |
| 2 | 10/19 | 120분 | 새 인물·새 자료. 카카오 로컬 모의 경계까지 포함 |
| 3 | 10/26 | 150분 | 실패 복구와 미확인 처리까지 묶음 완성 |

시간은 학습 설정이다. 공식은 10:00~15:00 5시간이며, 모의 시간이 길어질수록 공식에 가까워지는 게 아니라 "중간에 멈춰도 묶음이 완성되는가"를 연습하는 것이다. 공식 심사기준을 흉내 냈다고 주장하지 않는다.

각 모의전마다 [모의전 실습](../labs/06-mock-exams.md) 형식으로 준비·행동·산출물·예상 결과·막힘 분기를 채운다. 인물마다 목표가 달라야 하고, 지난 회차 답을 끼워 맞추면 그 회는 무효다. 평가는 평가표 규칙 그대로 — 고정 N, P/N, B=0, 미확인 명시, 모의/네이티브 분리.

## 규정이 안 열리거나 일정이 밀릴 때

- **상세 규정 미공개가 계속되면**: 모의 제출 묶음 완성까지가 종점. "제출 가능"으로 판정하지 않고, [제출 대조표](../templates/submission-checklist.md)의 "공개 규정 확인 후 채울 것" 칸을 비워 둔 채 미확인으로 남긴다.
- **접수 상충(상단 마감 vs 하단 10/21)**: 네가 직접 공식 경로·수신 메일로 확인한다. 확인 전까지 준비는 계속하되 "참가 확정"으로 적지 않는다.
- **모의전을 한 회 놓치면**: 뒤 회차에 합치지 말고 건너뛰고 남은 회를 정상 수행한다. 범위를 줄일 때는 확장 경로부터 버린다.
- **카카오 요구가 늦게 확인되면**: 연결 계약과 G 게이트로 판단한다. 승인·조건 확인 전의 실제 연결·새 계정·키·결제는 일정 압박과 무관하게 하지 않는다 — 이 과업에서 그런 행위가 없다는 뜻이지, 승인된 미래 심화 실습까지 금지한다는 뜻이 아니다.
- **링크가 막히면**: 공식 홈페이지를 다시 열어 같은 항목을 찾고, 못 찾으면 미확인으로 남긴다. 확인 못 한 링크를 근거로 쓰지 않는다.

## 공식 규정 확인 항목 (도착하면 채우는 체크리스트)

규정 이메일이 오면 순서대로 확인한다:

1. 제한시간과 시작/종료 방식 — 5시간 공지와 실제 규정이 같은지
2. 허용 도구·기존 코드·외부 도움의 범위 — FAQ의 "제한 없음"이 규정에서 좁혀지는지
3. 제작물에 요구하는 카카오 경로 — 계정 연동만인지, 채널 챗봇·API 구축인지
4. 제출 형식 — 파일/URL/API, 스키마, 심사자 접근 조건
5. 환경 인증 사진의 정확한 요건과 공용 네트워크 판정 기준
6. 개인정보·비밀값을 결과물에 포함하지 않는 규정이 있는지

확인한 항목은 [제출 대조표](../templates/submission-checklist.md)에 `공개 1차 자료 확인`으로, 못 찾은 항목은 `미확인`으로 적는다.
