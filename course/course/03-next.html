모든 단원의 공통 규칙:

  • 손으로 한다. 코드 작성은 기존 대화형 AI CLI 한 세션에 시키되, 명령 실행·입력 선택·출력 대조·원인 판별은 네가 한다. Herdr 워커 분할은 쓰지 않는다.
  • 새 학습 폴더에서만 만든다(practice/과목-단원/ 같은 이름). 논문 도구, 하네스, 실서비스는 수정하지 않는다 — 배울 구조가 필요하면 사본을 두고 거기서 한다.
  • 기본 경로의 모든 과제는 새 계정·API 키·결제 없이 닫히게 설계했다 — 기존 구독 CLI와 python3 표준 라이브러리, 가상 카드·장부로 충분하다. JS가 필요하면 pnpm만 쓰고 설치 없는 것을 우선한다. 이 과정이 그런 경로를 만들지 않는다는 뜻이지, 승인된 미래 심화 실습을 영구 금지한다는 뜻이 아니다.
  • 각 단원의 시험은 실행 전 분모를 고정하고, 두 집계를 나눠 기록한다 — 관찰 완료: 사전 고정 분모 N_obs 건의 실험·비교·재현을 실행하고 결과·원인 후보·증거를 남겼는가(완료는 실행 뒤 C_obs=N_obs, 즉 비율 C_obs/N_obs=1일 때)와 제작물 시험 N_prod = P_prod + F_prod + U_prod > 0(만든 결과물이 기대 행동을 충족하는가, 합격은 P_prod=N_prod). 관찰 과제의 완료는 제작물의 합격이 아니고, 하나의 P로 두 결론을 내지 않는다. 관찰 완료를 실물·모델·카카오·대회 합격으로 올리지 않고, 단원·종류가 다른 수를 합산한 전체 통과율도 만들지 않는다. 핵심 경계 위반 B=0은 두 집계에 공통이다. 양식은 시험표, 기록은 학습 기록.
  • 시간은 전부 교육 제안(30~90분)이다. 못 끝내면 중간 기록을 남기고 이어간다.
  • 첫 자료는 출처 원장에서 확인된 공식 문서다. 원문을 못 열면 접근 불가로 표시하고, 확인 못 한 링크는 근거로 쓰지 않는다. 단원별 대응은 학습 지도 §3·§3.1에 있다.
  • 가상 카드·장부·기록으로 하는 과제와 실제 도구 실행을 구분한다. 종이 위 모의 실행으로 실제 DB·저장소·권한 설정이 검증됐다고 보고하지 않는다.

CS 기초 6단원

CS-1. 동시성 — 왜 순서가 결과를 바꾸나

첫 개념: 두 실행 흐름이 같은 상태를 동시에 건드리면 결과가 순서에 달린다(경쟁 조건). 막는 도구는 원자적 동작과 잠금. 원리는 원리 교재 1장과 같다 — 여기서는 직접 깨 본다.

첫 자료: OSTEP 26장 §26.3~26.5 (공유 상태·실행 순서·임계 구역·원자성).

과제 (약 60분) — 파일: practice/cs1-concurrency/

  1. 고정 순서로 재현(기본, 카드/표): 공유값 0을 두고 두 작업 P1·P2가 각각 "읽기 → +1 → 쓰기"를 한다. 순서표를 직접 실행한다: - 순차: P1 전부 → P2 전부 → 최종 2 - 엇갈림: P1 읽기(0) → P2 읽기(0) → P1 쓰기(1) → P2 쓰기(1) → 최종 1 — 이게 잃어버린 갱신(lost update) 이다. - 두 결과를 나란히 적는다. 이 과제는 손으로 확정 재현되는 것이 본질이다.
  2. 장벽으로 확정 재현(선택, 실제 스크립트): 같은 입력(두 작업 각 1회)을 유지한 채, CLI 세션에 "읽은 뒤 wait-marker 파일이 생길 때까지 기다렸다 쓰는 절차"를 만들게 하고, 두 프로세스가 모두 읽기를 마친 뒤 동시에 쓰게 한다 — 손실이 우연이 아니라 설계로 발생해 최종 1이 나온다. 횟수를 늘린 확장(예: 각 20회 → 기대 40 또는 손실 관측)을 하려면 입력 횟수와 기대값을 다시 명시한 별도 실험이다.
  3. 자유 동시 실행(관측 전용): 장벽 없는 버전(같은 입력, 각 1회)을 두 터미널에서 돌려 결과를 여러 번 기록한다. 어떤 값이 나와도 합격/불합격 기준이 아니다 — 이 입력에서는 1도 2도 나올 수 있다. 나온 값의 범위를 "관측"으로 기록할 뿐 특정 값을 기대값으로 고정하지 않는다.
  4. 잠금 버전(mkdir 잠금 디렉터리)은 같은 입력(각 1회)으로 비교한다 — 잠금 버전의 기대는 =2.

시험 입력: 고정 순서표 2개(순차·엇갈림). 기대 결과: 엇갈림 순서에서 1, 순차에서 2를 도출. 자유 실행의 수치는 판정이 아니라 관측 기록.

스스로 설명: 잠금 없이도 2가 나오는 이유를 말한다(결과는 실행 순서의 함수 — 우연이 맞을 수 있어도 보장은 아니다). 잠금 하나가 외부 앱 상태까지 고정한다고 주장하지 않는다.

완료 기준: 순서표와 두 결과(1·2)의 도출 기록. N_obs=2(순서표 2건) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰·도출 과제다. 자유 실행 결과는 분모에서 제외된 관측 항목으로 표시한다.

CS-2. 네트워크 — 어느 층에서 죽었나

첫 개념: 요청은 DNS(이름→주소) → 연결 → 요청/응답 층을 지난다. 실패는 층마다 다르고, 층이 다르면 원인 후보가 다르다. 원리는 원리 교재 4장.

첫 자료: RFC 9110 §9.2.2(멱등 메서드), §15.6.3(502), §15.6.5(504) — 긴 표준이니 지정된 절만 읽는다.

과제 (약 60분) — 폴더: practice/cs2-network/ (서버는 이 폴더 안에서만 띄운다 — 서버는 실행 위치의 파일을 노출하므로 새 학습 폴더로 이동 후 시작)

  1. 포트부터 확인: curl --disable -v --noproxy "*" --max-time 5 http://127.0.0.1:8000/를 먼저 두드린다. 무엇인가 응답하면 그 포트는 이미 남의 서버가 쓰고 있다 — 그 서버를 끄지 말고 다른 포트(예: 8010)를 골라 이후 모든 주소를 바꾼다. 그다음 cd practice/cs2-network 후 python3 -m http.server 8000 --bind 127.0.0.1로 로컬 서버를 띄운다(본인 컴퓨터 안에서만 받게 묶는다).
  2. 다른 터미널에서 정상 요청: curl --disable -v --noproxy "*" --max-time 5 http://127.0.0.1:8000/ — 출력의 연결 단계와 응답 헤더를 읽는다. --disable은 첫 옵션으로 둘 때만 개인 curl 설정 파일을 무시하고, --noproxy "*"는 프록시 환경 변수의 영향을 끊어 이 실험을 직접 연결로 고정한다 — 환경의 실제 설정을 바꾸거나 내용을 출력하지 않는다.
  3. DNS 실패 재현: curl --disable -v --noproxy "*" --max-time 5 http://nonexistent.invalid/ — .invalid는 실험용으로 예약된 끝자리라 로컬 이름 해석 실패가 예상된다. 출력에서 "resolve"가 안 되는 지점을 찾는다. 프록시를 끊지 않은 명령에서 나온 오류는 DNS 실패로 단정하지 않는다 — 프록시가 대상 호스트를 대신 조회할 수 있어 오류의 주체가 다를 수 있다.
  4. 연결 실패 재현: 서버를 멈추고 같은 주소로 curl --disable -v --noproxy "*" --max-time 5 http://127.0.0.1:8000/ — connection refused를 본다.
  5. 응답 대기 timeout 재현: CLI 세션에 "127.0.0.1에만 묶이고, 연결은 받되 응답을 절대 안 돌려주며, 연결 수락과 요청 수신을 로그로 남기는 서버"를 practice/cs2-network/ 안에 만들게 한다. curl --disable -v --noproxy "*" --max-time 3 http://127.0.0.1:8001/로 요청한다 — 서버 로그의 "연결 수락·요청 수신"이 "연결·요청은 갔고 응답 대기에서 걸렸다"의 관측 근거다. 이 근거 없이 시간 초과만 보고 층을 확정하지 않는다.
  6. 세 실패 출력을 나란히 놓고 어느 층인지 분류 표를 만든다 — 각 칸에 관측 근거(오류 문구·서버 로그)를 함께 적고, 근거가 없거나 예상과 다른 출력은 가정하지 말고 미확인으로 적는다.

시험 입력: 위 3~5의 세 가지 실패. 기대 결과: 각 출력에서 실패 층(DNS/연결/응답 대기)을 관측 근거와 함께 지목. 근거 없는 분류는 미확인으로 남긴다.

스스로 설명: 502가 "내 요청이 틀렸다"를 뜻하지 않는 이유. 멱등하지 않은 요청의 자동 재시도가 왜 위험한가(원리 2장과 연결).

완료 기준: 분류 표 + 세 실패의 출력 저장. N_obs=3(세 실패의 분류 기록) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다. 실제 출력이 예상과 달라도 그것을 관측·미확인으로 기록하면 완료다.

CS-3. 데이터베이스 — 트랜잭션과 색인

첫 개념: "잔액 A에서 B로 옮기기"는 빼기+더하기 두 동작이다. 중간에 죽으면 반쪽만 반영된다. 트랜잭션은 묶인 동작을 전부 확정(COMMIT) 또는 전부 취소(ROLLBACK)로 만든다 — 원자성의 데이터베이스 판. 인덱스(색인) 는 책 뒤의 찾아보기처럼, 행을 다 뒤지지 않고 위치로 바로 가는 별도 자료구조 — 검색은 빨라지지만 행이 바뀔 때마다 색인도 갱신하는 유지 비용이 있다.

첫 자료: PostgreSQL 트랜잭션 §3.4(S04)의 첫 설명과 BEGIN/COMMIT/ROLLBACK 문단(SQL은 건너뛰어도 됨), PostgreSQL 인덱스 소개 §11.1(S05)의 책 색인 비유·사용 선택·유지 비용 부분.

과제 (약 60분) — 파일: practice/cs3-db/ (가상 장부 과제라 DB 설치 불필요)

  1. 장부 계산: 계정 A=100, B=50에서 20을 옮기는 가상 장부를 종이/텍스트로 만든다. 세 경우를 계산한다: - 두 변경 모두 확정 → 결과 (80, 70) - 빼기만 하고 중간 실패 → 전체 취소 → 결과 (100, 50) - 빼기만 저장(부분 저장) → 결과 (80, 50) - 합계를 비교한다: 앞의 둘은 150, 부분 저장은 130 — 이 130이 "반쪽 상태"다.
  2. 색인 실험: ID가 섞인 자료 카드 8행을 만든다. (a) 8행을 처음부터 다 읽는 방법과 (b) ID→행 위치를 적은 색인 카드로 찾는 방법으로 같은 ID를 찾는다. 각 방법이 실제로 조사한 항목 수를 기록한다.
  3. 새 행 하나를 추가하고, 색인 카드에서 무엇을 바꿔야 하는지 표시한다 — 이게 유지 비용.

선택 확장: command -v sqlite3로 존재를 먼저 확인한다. 있으면 같은 이체를 BEGIN;/COMMIT;/ROLLBACK;으로 실제 실행해 본다. 없으면 설치하지 않는다 — 가상 장부 과제만으로 이 단원은 완료된다. 실제 실행을 했다면 학습 기록에 별도로 표시한다.

시험 입력: 이체 20의 세 경우, ID 찾기 2회(두 방법). 기대 결과: 세 결과 (80,70)·(100,50)·(80,50)과 합계 도출, 두 방법이 같은 행을 찾되 조사 항목 수가 다름.

스스로 설명: 트랜잭션 밖의 효과(이미 보낸 메시지)도 롤백되나? — 아니다. 트랜잭션은 그 DB의 변경만 묶는다. 색인이 있으면 항상 빠른가? — 아니다. 색인을 쓸지는 엔진이 고르고, 유지 비용 때문에 늘릴수록 쓰기가 느려진다.

완료 기준: 장부 세 경우와 색인 조사 수 기록. N_obs=5(장부 3 + 색인 2) — 완료는 실행 뒤 C_obs=N_obs일 때다. 도출·관찰 과제다. 가상 과제의 결과를 실제 PostgreSQL 동작 검증으로 보고하지 않는다.

CS-4. 파일시스템과 권한 — 거절의 두 층

첫 개념: 파일 권한(rwx)과 macOS의 앱별 접근 허용(시스템이 앱 단위로 파일·폴더 접근을 묻는 층)은 별개 층이다. "주체가 누구인가"가 진단을 가른다. 원리는 원리 교재 5장.

첫 자료: Apple Mac 사용 설명서 — 파일 및 폴더 접근 제어(S07)의 Files & Folders 권한 설명과 설정 위치 부분. 권한 비트(모드) 표기는 man chmod의 숫자 표기 부분을 함께 본다.

과제 (약 45분) — 파일: practice/cs4-perms/ (가상 표와 사본 폴더에서만. 실제 문서 폴더·설정 변경 금지)

  1. 가상 허용 표: 같은 폴더 위치에 앱 A는 거부, 앱 B는 허용이라는 가상 표를 만든다. 칸은 넷 — 요청 앱 / 대상 위치 / 허용 여부 / 그 근거.
  2. 문서상 확인 위치 메모: S07이 안내하는 설정 화면 위치를 메모한다. 네 Mac의 실제 목록은 열어서 보기만 하고 기록한다(토글 변경 금지, 실제 상태는 미확인으로 유지).
  3. rwx 층 재현: 사본 폴더에 secret.txt를 만들고 chmod 000으로 권한을 뺀다. CLI 세션에 읽기를 시켜 실패 오류 문구를 기록하고, chmod 644로 복원해 성공을 확인한다.

시험 입력: 가상 표 4칸 + 권한 000 파일 읽기. 기대 결과: TCC 층은 가상 표(가상 사례 1종)로, rwx 층은 사본 파일의 실제 실행(실측 사례 1종)으로 각각 다룬다 — 가상 표 완성을 실제 TCC 거절 재현으로 세지 않는다. 두 층을 구별해 앱 권한 문제를 파일 권한 문제로 오진하지 않음.

스스로 설명: Permission denied가 보일 때와 조용히 실패할 때의 층 차이. 접근 실패를 곧바로 "모델 오류"나 "권한 다 열기"로 닫으면 안 되는 이유.

완료 기준: 가상 표 4칸(TCC 층의 가상 사례) + chmod 000 실패·chmod 644 성공의 출력 저장(rwx 층의 실측 사례). N_obs=2 — 완료는 실행 뒤 C_obs=N_obs일 때다. 네 Mac의 실제 권한 상태를 확인했다고 주장하지 않는다.

CS-5. git 내부 — 커밋은 스냅샷, 브랜치는 포인터

첫 개념: git은 파일 내용 덩어리(blob), 파일명→내용을 묶은 목록(tree), 부모와 트리를 가리키는 설명서(commit)의 쌓임이다. 브랜치는 커밋 하나를 가리키는 움직이는 이름표일 뿐이다. 병합은 보통 두 부모를 가리키는 새 커밋을 만들지만, 한쪽이 다른 쪽의 그대로 이어진 앞부분이면 새 커밋 없이 이름표만 앞으로 옮긴다(fast-forward) — "병합 = 새 커밋"은 예외가 있다.

첫 자료: Pro Git — Git Objects(S06)의 blob 설명·Tree Objects·Commit Objects 부분.

과제 (약 45분) — 파일: practice/cs5-git/ — 카드 모의가 기본 과제이며 이 단원은 실제 저장소를 만들지 않는다.

  1. 네 종류의 카드를 쓴다 — 파일 내용 카드(blob), 파일명→내용 카드(tree), 부모·트리·설명 카드(commit), 이름표 카드(branch).
  2. 파일 2개짜리 버전 1의 카드 그림을 그린다. 이름표 main이 그 commit을 가리키게 한다.
  3. 버전 2에서 파일 하나만 바꾼다 — 새 blob, 새 tree, 새 commit을 이어 붙이고 부모 화살표를 그린다. 이름표가 새 commit을 가리키게 옮긴다.
  4. commit 카드의 "부모" 화살표만 따라가 버전 1 시점의 파일 내용을 복원한다.
  5. fast-forward 확인: 버전 1 뒤에 버전 2가 일렬로 붙은 상황에서 이름표만 옮기는 것과, 양쪽이 갈라진 뒤 만나는 것(새 commit, 부모 2개)을 카드로 나란히 그려 둘을 구분한다.

실제 저장소 실습은 이 단원에서 하지 않는다. 커밋을 만드는 연습은 커밋·푸시 게이트 배선이 확인된 새 폴더에서만 별도 과제로 한다 — 게이트 없는 저장소에 커밋하지 않는 규칙이 먼저다. 그때도 reset --hard·clean -fdx·force push·main merge는 금지다.

시험 입력: 카드 이력 2건(일렬 연장 1, 갈라져 만나는 병합 1). 기대 결과: blob/tree/commit/branch 역할 구별, 부모 화살표로 이전 시점 복원, fast-forward와 병합 커밋 구분.

스스로 설명: "브랜치를 삭제하면 커밋이 사라지나?" — 해설: 이름표만 사라진다. 객체는 다른 이름표·태그가 가리키거나 보존 기간 안에는 남지만, 아무 참조도 없으면 나중에 정리(garbage collection)될 수 있다 — "영원히 남는다"도 틀린다. 커밋을 만들었다고 원격 저장·배포까지 했다고 보고하지 않는다.

완료 기준: 카드 이력 그림 2건 + 복원 설명. N_obs=2 — 완료는 실행 뒤 C_obs=N_obs일 때다. 도출·관찰 과제다. 카드 모의를 실제 저장소 조작으로 보고하지 않는다.

CS-6. 보안 기초 — 누가 무엇을 할 수 있는가

첫 개념: 인증(authentication — 네가 누구인지 확인)과 인가(authorization — 이 요청이 허용되는지 판정)는 다른 단계다. 로그인에 성공해도 개별 작업이 허용되는 건 아니다. 최소 권한은 "필요한 것만 열고 나머지는 기본 거부(deny by default)", 그리고 요청마다 다시 검증하는 것이 원칙.

첫 자료: OWASP Authentication Cheat Sheet(S08)의 Introduction·Authentication Responses 부분, OWASP Authorization Cheat Sheet(S09)의 Least Privileges·Deny by Default·Validate Permissions on Every Request 부분.

과제 (약 60분) — 파일: practice/cs6-security/ (가상 카드와 표로, 실제 계정·로그인 변경 없음)

  1. 인증 응답 설계: 가상 결과 넷 — 로그인 성공 / 잘못된 증명 / 없는 계정 / 잠긴 계정 — 에 대해 사용자에게 보여줄 응답 문구를 적는다. 조건: 네 실패 문구가 서로 구분돼선 안 된다(문구만으로 "계정이 있냐 없냐"를 알아내지 못하게). 내부용 원인 분류와 외부용 문구를 별도 칸으로 쓴다.
  2. 인가 표: 역할 둘(조회 전용 / 변경 담당) × 자료 A·B × 동작 셋(읽기·수정·발송)의 권한표를 만든다. 허용 칸마다 "왜 필요한가"를 적고, 표에 없는 요청은 기본 거부로 처리한다.
  3. 반례 시험: (a) 인증 성공했지만 이 요청 권한이 없는 경우, (b) 이전 요청은 허용됐지만 다음 요청은 권한이 없는 경우 — 둘 다 거부로 나오는지 표에서 확인한다.
  4. 도구에 적용: 가상 도구 3개(파일 읽기, 파일 쓰기, 메시지 발송)에 같은 표를 적용해 최소 권한 규칙을 정한다 — 예: 발송은 사람 승인 없이 불가.

시험 입력: 인증 응답 4개 + 권한표 + 반례 2개. 기대 결과: 실패 문구로 계정 존재를 알 수 없음, 미지정 요청은 거부, 반례 둘 다 거부.

스스로 설명: 인증 성공이 왜 인가를 대신하지 못하는가. "요청마다 검증"이 왜 필요한가(이전 허용을 다음 요청의 근거로 쓰면 안 되는 이유).

완료 기준: 응답 표 + 권한표 + 반례 결과. 제작물 시험이다 — N_prod=3(응답 설계·인가 표·반례 검증), P_prod=3이 합격 조건. 실제 비밀번호·토큰을 기록에 적지 않는다.

AI-1. LLM의 작동과 컨텍스트 — 창 안의 세계

첫 개념: 모델은 다음 토큰의 확률을 내는 기계다. 창(context window) 안에 있는 것만 읽고, 창은 유한하다. 대화가 길어지면 중요한 것이 밀려난다 — 원리는 원리 교재 6장.

첫 자료: Google ML Crash Course — LLM 소개(A05)의 "What is a language model?"과 "Context" 부분. 이어서 컨텍스트 엔지니어링 글(A03)의 선별·압축·외부 노트 부분.

과제 (약 60분) — 파일: practice/ai1-context/

  1. 확률 표 먼저: 후보 토큰 셋에 확률 0.6·0.3·0.1을 적고, 매번 최대값만 고르는 방식과 확률대로 뽑는 방식의 차이를 표로 비교한다. 합이 1인지 확인하고, "가장 확률 높은 출력"과 "가능한 출력"을 구분해 적는다. 이 확률은 사실의 참일 확률이 아니다.
  2. 같은 질문 3개를 두 조건에서 던진다 — 새 대화(짧음)와 긴 대화 끝(규칙·잡담 수십 턴 뒤). 답이 달라지는지 기록한다.
  3. 규칙 하나(예: "항상 근거 파일명을 써라")를 첫 턴에 두고, 긴 대화 뒤 위반하는지 본다.
  4. 세 번째 조건: 긴 대화 끝에서 규칙 재주입(마지막에 다시 명시)한 뒤 같은 질문 3개를 다시 던져 전후를 비교한다.
  5. 기록에 "재주입은 확률이지 보장이 아니다"가 성립하는지 자기 관찰로 판단한다.

시험 입력: 질문 3 × 조건 3(짧음 · 긺 · 긺+재주입) = 관찰 9건. 기대 결과: 각 관찰에 답·창 위치·재주입 여부를 기록 — 결과 차이가 없어도 관찰은 완료다.

스스로 설명: 왜 모델은 "아까 한 말"을 못 믿는가. 압축의 손실이란 무엇인가.

완료 기준: 비교 기록 1개. N_obs=9(질문 3 × 조건 3) — 완료는 실행 뒤 C_obs=N_obs일 때다. 차이가 없어도 완료 — 차이를 기대값으로 두지 않는다. 목적은 예측이 아니라 관찰이다.

AI-2. workflow와 agent — 고정 절차냐 모델 판단이냐

첫 개념: 다음 단계를 사람이 정해두면 workflow, 모델이 도구를 골라가며 멈출 때까지 돌면 agent. 단순한 것부터 시작해 필요할 때만 복잡하게.

첫 자료: Building effective agents(A01)의 "What are agents?·When (and when not)" 부분, OpenAI 에이전트 안내(A02)의 단일 에이전트·종료 조건 부분.

과제 (약 90분) — 파일: practice/ai2-workflow-agent/

  1. 같은 작업(예: 자료 파일 3개를 읽고 결정표 만들기)을 두 방식으로 엮는다: - 고정 절차(workflow — 사람이 실행기): 네가 단계를 나누고 각 단계를 별도 호출로 실행한다 — "1단계: 자료 파일 3개를 읽어 각각 표 행으로 정리해" → 네가 출력을 확인하고 다음 입력을 만든다 → "2단계: 이 표에서 비어 있는 항목을 미확인으로 표시해" → 네가 확인. 각 단계의 입력·출력·다음 단계로의 진행은 네가 통제하고, 모델은 단계 안에서만 답한다. 단계를 나눠도 입력 범위는 자료 3개 전체로 같다 — 고정 절차 쪽이 일부 파일만 보게 줄이지 않는다. - 모델 주도(agent): 도구(파일 읽기)와 종료 조건("표의 빈칸이 없으면 멈춰라")만 주고 한 세션이 순서를 정하게 둔다.
  2. 같은 입력 3개를 둘에 넣고 결과·소요·예측 가능성을 비교한다 — 고정 절차 쪽에서 "다음에 무엇을 하는가"를 결정한 주체가 너인지 함께 기록한다.

시험 입력: 같은 입력 3개 × 방식 2 = 관찰 6건. 기대 결과: 각 방식의 산출물과 "어느 쪽이 왜 나았나" 판단 기록.

스스로 설명: agent가 나은 조건과 workflow가 나은 조건을 각각 하나씩. 그리고 고정 절차에서 다음 단계를 정한 주체는 누구인가 — 단계를 나열한 프롬프트 하나에 맡겼다면 그건 모델이 순서를 따를지 "선택"하는 것이지 구조가 고정한 것이 아니다.

완료 기준: 비교 기록 1개. N_obs=6(입력 3 × 방식 2) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다. 어느 방식이 이겼는가는 판정값이 아니고, "방식별 실패 모습"을 비교하는 게 목적이다.

AI-3. RAG — 올라오는 조각이 답을 정한다

첫 개념: 자료를 조각(청크)으로 잘라 두고, 질문과 가까운 순으로 k개(top-k)를 꺼내 모델에 붙인다. 답의 품질은 어떤 조각이 올라왔는지가 좌우한다.

첫 자료: RAG 논문 초록(A06) — 학습된 지식과 검색 자료의 결합이라는 원리 부분만 본다.

과제 (약 60분) — 파일: practice/ai3-rag/

  1. 가상 문서 5개(각 3~5문장, 서로 다른 주제)를 만든다. 그중 하나에는 문장 사이 의존이 있는 쌍을 넣는다 — 예: "김 씨는 2020년에 입사했다. 그해 그는 팀장이 됐다."(둘째 문장의 "그해"는 첫째 없이는 해석이 안 된다).
  2. 청킹 실험: 문장 단위로 자른 버전과 단락 단위로 자른 버전을 준비한다. 문장 경계를 지켜 자르니 "문장 중간 절단"은 이 실험에서 일어나지 않는다 — 보려는 것은 문장 사이 의존이 끊기는 경우다.
  3. 질문 3개를 정한다 — 하나는 의존 쌍을 건드린다(예: "김 씨가 팀장이 된 해는?"). 각 버전에서 "top-2로 올릴 조각"을 네가 직접 고른다(검색 역할을 손으로 재현).
  4. 올라온 조각만 붙여 CLI에 답을 시키고, 청킹 버전별 답을 기록한다. 차이가 없어도 유효한 관찰이다 — 양쪽 조각이 답에 충분한 근거를 담았다는 결론일 수 있다.
  5. 틀린 답이 나오면 원인을 둘로 나눈다 — 필요한 조각이 안 올라온 검색 누락인지, 올라왔는데 잘못 쓴 생성 오류인지.

시험 입력: 질문 3 × 청킹 2 = 관찰 6건. 기대 결과: 각 관찰에 선택한 조각·답·(틀렸다면) 검색/생성 구분 기록. 차이 사례는 합격 조건이 아니다 — 차이만 골라 모아 "청킹 효과"로 주장하지 않는다.

스스로 설명: top-k를 늘리면 왜 항상 좋아지지 않는가(관련 없는 조각이 섞임). 틀린 답에서 검색 누락과 생성 오류를 어떻게 나눠 보나 — "어느 쪽이 더 중요한가"를 이 한 실험으로 일반화하지 않는다.

완료 기준: 조각 선택 표 + 답 비교 + 원인 구분 기록. N_obs=6(질문 3 × 청킹 2) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다.

AI-4. 도구와 구조화 출력 — 계약을 종이에 쓰기

첫 개념: 도구는 이름·입력·출력·실패 형식의 계약이다. 출력 형식을 스키마로 강제하면(구조화 출력) 파싱이 안정되지만, 형식이 맞다고 내용이 맞는 건 아니다.

첫 자료: MCP 도구 명세(A07)의 Tool·Output Schema·Error Handling 부분, JSON Schema object(A08)의 Properties·Required 부분.

과제 (약 60분) — 파일: practice/ai4-tools/

  1. 도구 하나(예: find_note(query) → {results: [{id, title}]})의 입출력 스키마를 직접 적는다 — 필수 필드, 타입, 실패 시 형식까지.
  2. CLI에 "이 스키마대로만 답하는 작은 프로그램"을 만들게 한다.
  3. 형식 검증 실험: 스키마를 어긴 출력(필드 누락, 타입 다른 값)을 일부러 만들어 검증기가 걸러내는지 본다.
  4. 의미 검증 실험: 형식은 맞지만 내용이 틀린 출력(존재하지 않는 근거 ID)을 통과시키는지 본다 — 통과하면 "형식 통과 ≠ 정답"의 직접 증거.

시험 입력: 정상 1, 형식 오류 2, 의미 오류 1. 기대 결과: 형식 오류는 걸러지고 의미 오류는 형식 검사를 통과함을 확인한다 — 이것은 검증기 범위의 관찰이다.

스스로 설명: 프로토콜 오류와 도구 실행 오류의 구분. 의미 검증에는 무엇이 더 필요한가.

완료 기준: 스키마 문서 + 4개 입력의 검증 결과. 집계를 둘로 나눈다 — 제작물 시험 N_prod=3(정상 통과 1 + 형식 오류 거부 2)이 형식 검증기의 합격 조건(실행 뒤 P_prod=N_prod)이고, 의미 오류는 관찰 N_obs=1의 대상으로 기록하되 그 출력 자체는 의미 정확성 기준으로 실패라고 별도 적는다. 의미 오류의 형식 통과를 제작물 성공으로 세지 않는다.

AI-5. 평가 — 정답 없는 것을 재는 법

첫 개념: 실패 사례에서 시험을 만들고, 기준을 미리 적고, 판정자의 편향을 관리한다. 지금까지 10월 내내 해 온 것의 심화판.

첫 자료: Your AI Product Needs Evals(A04)의 평가 유형·Level 1·시험 사례 부분.

과제 (약 90분) — 파일: practice/ai5-evals/

  1. 모의전 산출물 중 하나를 골라 그 실패 이력에서 새 시험 8개를 설계한다 — 개발용 4 + 확인용 4로 분리.
  2. LLM 판정자 편향 실험: 같은 답 두 개의 순서를 바꿔 판정시키거나, 짧은 답/긴 답을 비교시켜 판정이 흔들리는지 본다.
  3. 판정자가 AI여도 실행 로그와 근거 원문을 직접 대조해 판정이 맞는지 확인한다.

시험 입력: 설계한 시험 8개 + 편향 실험 2개. 기대 결과: 제작물 시험의 P_prod/N_prod 기록 + 판정 불일치 관찰(있으면) 분석.

스스로 설명: 개발용과 확인용을 섞으면 왜 평가가 무너지는가. 판정자 편향이 크면 무엇을 바꾸나(기준을 더 구체적으로/사람 샘플 대조).

완료 기준: 시험표 버전 2개(개발용/확인용), 집계 분리 기록 — 제작물 시험 N_prod=8과 판정자 관찰 N_obs=2를 별도로 센다(관찰 완료는 실행 뒤 C_obs=N_obs일 때). 제작물이 P_prod<8이어도 단원 완료는 가능하나 기록은 필수다.

운영 4단원

OPS-1. 관측 — 증상과 원인을 나눈다

첫 개념: "느리다"는 증상이고 원인이 아니다. 지연·요청량·오류·포화도 네 신호로 시스템을 본다.

첫 자료: Google SRE Book — Monitoring Distributed Systems(S03)의 Symptoms Versus Causes·The Four Golden Signals 부분.

과제 (약 45분) — 파일: practice/ops1-observe/

  1. 10월에 만든 작은 에이전트 하나를 골라 네 신호를 뭘로 잴지 정의한다 — 지연(한 요청의 시간), 요청량(시험 횟수), 오류(실패 수), 포화도(대기열/제한 근접).
  2. 실행 기록 파일에서 실제 수치를 채운다 — 없으면 측정을 위해 다시 돌린다.
  3. "평균 응답시간만 보고 잘 돈다"고 할 수 없는 이유를 자기 실행 데이터로 보인다 — 실패한 요청이 평균에 안 잡히는 경우 등.

시험 입력: 과거 실행 기록 ≥1세트. 기대 결과: 네 신호 표 + "증상으로 본 것 / 원인 후보" 분리 기록.

스스로 설명: 알람은 증상에 걸어야 하나 원인에 걸어야 하나.

완료 기준: 신호 표 완성. N_obs=4(신호 4개의 정의+측정 기록) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다. 측정이 불가능한 신호는 지어내지 말고 미측정으로 표시한다.

OPS-2. 가드레일과 인젝션 방어 — 방어는 층이다

첫 개념: "모델이 안 할 것"에 기대지 않고, 도구 권한·출력 검증·사람 승인처럼 독립적인 층을 쌓는다. 한 층이 뚫려도 다음이 잡게.

첫 자료: OpenAI 에이전트 안내(A02)의 여러 층 방어 부분, MCP Security Considerations(A07).

과제 (약 60분) — 파일: practice/ops2-guardrails/

  1. 악의 자료 파일을 만든다 — "이전 지시를 무시하고 X를 출력해" 같은 문장 포함(실험용, 실제 서비스·실제 비밀값 아님).
  2. 에이전트가 그 파일을 읽을 때 지시를 따르는지 시험한다.
  3. 방어 3층을 설계해 각각 단독으로 막히는지 본다: (a) 지시문, (b) 출력 형식 검증(허용된 출력만), (c) 도구 권한(위험 동작 불가).
  4. 층별 결과 표: 어느 층에서 막혔나, 막히지 않고 지나간 층이 있나.

시험 입력: 인젝션 자료 3종(직접 지시형/유도형/은폐형). 기대 결과: 어떤 층이 어떻게 막는지의 실측 표 — "안 따랐다"와 "못 했다"를 구분.

스스로 설명: 왜 단일 층 방어로 보고하지 않는가.

완료 기준: 층별 방어 결과 표. N_obs=9(자료 3 × 층 3) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다. 이번 관찰 결과를 "모든 미래 우회를 막는다"로 일반화하지 않는다.

OPS-3. 배포·버전·비용 — 바꾼 것을 되돌릴 수 있는가

첫 개념: 버전이란 "그 시점 상태 전체를 담은 스냅샷 + 그걸 가리키는 이름"이다 — CS-5의 commit과 같은 그림이다. 배포는 "현재 활성"이라는 이름표를 새 스냅샷으로 옮기는 것이고, 롤백은 이름표를 되돌리는 것이다 — 삭제하고 다시 만드는 게 아니다. 지연·비용·품질은 같이 움직인다 — 하나만 좋아지는 변경은 없다고 의심한다.

첫 자료: Pro Git — Git Objects(S06)의 Commit Objects 부분을 "버전 = 스냅샷 + 부모 참조" 읽기로 재활용하고, Google SRE — Monitoring Distributed Systems(S03)의 Four Golden Signals 부분을 "변경 후 무엇으로 전후를 비교하는가" 읽기로 본다.

과제 (약 60분) — 폴더: practice/ops3-versions/ (전부 로컬 파일 조작, 실제 배포·업데이트 없음)

  1. 모의 배포 구조를 만든다: - release-A/와 release-B/ 두 폴더에 각각 결과물을 둔다 — B는 A를 고친 버전. 결과물은 결정적 생성 규칙이어야 한다 — 같은 입력이면 항상 같은 출력이 나오는 규칙 파일(예: 입력을 정해진 표로 바꾸는 변환 규칙). 출력이 매번 흔들리는 대상(모델 호출 등)은 이 기본 과제의 전제와 맞지 않는다. - manifest-A.txt·manifest-B.txt에 각 버전의 파일 목록과 "무엇이 바뀌었나"를 적는다. - current.txt에 활성 버전 이름을 적는다 — 이게 상태 포인터.
  2. 같은 시험 입력을 A가 활성일 때 돌려 출력을 저장한다.
  3. current.txt를 A→B로 바꾸고(전환) 같은 시험을 돌린다. 출력과 manifest를 대조한다.
  4. current.txt를 B→A로 되돌리고(롤백) 같은 시험을 다시 돌려, A 시절 출력과 같은지 확인한다 — "돌렸다"의 증거는 되돌린 뒤의 재실행 출력이다.
  5. 관측 표를 채운다: 각 실행의 소요 시간(지연), 돌린 시험 수(요청량), 실패 수(오류)를 측정하고, 자료 크기는 부하 크기의 관측으로만 기록한다. 포화도는 미측정으로 표시한다 — 이 모의에는 가용 용량·한계를 정의하지 않았으므로 근사치조차 아니다.

시험 입력: 고정 시험 1세트 × 실행 3회(A·B·A'). 기대 결과(제작물 판정): ①A' 실행의 파일·포인터·출력이 A 실행과 같다 — 결정적 규칙 전제에서만 닫히는 조건이다, ②B의 출력 차이가 manifest-B에 적힌 변경 범위 안이다. 출력 불일치를 곧장 롤백 실패로 읽지 않는다 — 비결정적 결과물을 썼다면 전제 위반이니 설계를 다시 고친다.

스스로 설명: 포인터 전환과 파일 덮어쓰기의 차이는? — 해설: 덮어쓰기는 옛 상태를 지운다. 포인터는 두 버전을 둘 다 보존한 채 가리키는 대상만 바꾸므로 되돌림이 재구성이 아니라 한 줄 변경이다. 전환 순간과 관측 사이에 무엇이 끼어들 수 있나(캐시된 옛 결과 등)?

선택 심화(별도 구분): 실제 CLI 업데이트·롤백, 실제 가격·토큰 비용, 원격 배포는 이 과정에서 검증되지 않았다. 필요하면 승인·조건 확인 후 별도 작업이다 — 이 단원의 합격과 무관하다.

완료 기준: manifest 2개 + 포인터 전환/되돌림 기록 + 관측 표. 제작물 시험 N_prod=2(전환, 롤백 복원 — 실행 뒤 P_prod=N_prod가 합격)와 관찰 N_obs=4(지연·요청량·오류 측정 + 포화도 미측정 표시 — 완료 목표는 실행 뒤 C_obs=N_obs일 때)를 별도로 센다. 측정하지 않은 신호를 수치로 채우는 것은 미측정 위반이다.

OPS-4. 단일에서 다중으로 — 분리가 사는 것과 비용

첫 개념: 하나의 세션이 하던 일을 여러 세션으로 나누면 격리·검토 분리·병렬화를 얻지만, 조정 비용·경계 계약·새 실패 모드(소통 오류)를 산다. 원칙은 "단일 에이전트가 먼저 돌고, 분리는 그것이 한계에 닿았을 때".

첫 자료: OpenAI 안내(A02)의 단일→다중 확장 부분, Anthropic(A01)의 오케스트레이터-워커 부분.

과제 (약 90분) — 파일: practice/ops4-multi/

  1. 10월 과제 하나(인터뷰→요구→구현→시험)를 두 세션으로 나눠 재수행한다: 세션A가 요구 계약까지, 세션B가 구현·시험. 네가 중간에서 계약 문서만 넘긴다.
  2. 소통 계약을 먼저 적는다 — 의도만 주고 설계는 받은 쪽이 한다는 경계를 문장으로.
  3. 단일 세션 결과와 비교한다: 품질, 소요 시간, 새로 생긴 실패(계약 해석 차이 등).
  4. 분석 결론: 어떤 작업에서 분리가 이득이고 어떤 작업에서 손해인지 자기 사례로 적는다.

시험 입력: 같은 과제 × 단일/분리. 기대 결과: 양쪽 산출물과 비교 기록. 실제 다중 호출은 보이는 대화형 CLI 세션으로만 — 숨은 호출·스크립트 경유는 이 과제 범위 밖.

스스로 설명: 네가 운영하는 책임자-워커-검토 분리가 이 원리에서 무엇을 사고 무엇을 치르는가.

완료 기준: 비교 기록 1개 + 계약 문서 1개. N_obs=2(두 방식 수행·비교) — 완료는 실행 뒤 C_obs=N_obs일 때다. 관찰 과제다.

과정 전체의 완주 정의

15단원을 다 돌았다고 끝이 아니다. 끝의 판정은 이것이다: 새로운 장애를 만났을 때, 그것을 어느 층의 문제인지 짚고, 구별 시험을 설계하고, 고친 뒤 같은 시험으로 증명하는 일을 혼자 할 수 있는가. 그게 되면 과정은 끝났다 — 그 뒤는 네가 스스로 다음 단원을 만든다.
